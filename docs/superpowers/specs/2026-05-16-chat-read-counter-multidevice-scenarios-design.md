# Chat Read-Counter Multi-Device Scenario Suite — Design

**Status:** approved design, pre-plan
**Date:** 2026-05-16
**Related:** GO-7290. **The chosen design is `2026-05-16-chat-read-counter-design.md` (OrderId+AddSeq dominance watermark). The earlier "engine redesign / option A vs B / DAG-preserving" program was deleted as over-engineering — ignore any "behavior-preserving"/"option B"/"DAG-exact" framing below.** This suite's role is now the **semantic sign-off artifact**: run with the watermark engine, non-crux scenarios must MATCH the recorded DAG baseline; the two crux scenarios (`S-concurrent-merge-divergence`, `S-cat12-dag-ancestor-vs-orderid-prefix`) MUST DIVERGE — that recorded divergence *is* the accepted-semantic decision. The harness/catalog/report code remains exactly as committed; only its interpretation changed.

## 1. Purpose & Differential Intent

The seenHeads → read-counter translation (any-sync `objecttree.DiffManager` driven by `sourceimpl.store`, consumed by chat `markRead*` → `chatrepository` unread counts) is **currently uncovered** in anytype-heart: existing `chatobject` tests mock the source (`source.EXPECT().InitDiffManager(...)`, `MarkSeenHeads(...).RunAndReturn(...)`).

Before any redesign (the proposed OrderId-prefix / AddSeq-watermark model), we build a **deterministic, reusable scenario suite** that exercises the *real* current pipeline across multi-device collaboration situations and records, per scenario, **two** things:

- **Intended** outcome — authored from first principles (what read counts *should* be).
- **Current-actual** outcome — recorded by running the scenario on today's system.

Divergence between them is a **finding**, surfaced for human decision (current bug to preserve vs. bug the redesign should fix) — never silently blessed. The same suite later runs against the redesign as a differential gate.

This phase makes **no production code changes** — characterization only.

## 2. Scope

**In scope:** a Go table-driven scenario harness; a catalog of multi-device scenarios; one characterization test per scenario; a report of intended vs current-actual.

**Out of scope:** the redesign itself; any any-sync changes; a network/transport sync simulator (we simulate only the seenHeads-merge boundary, not transport); performance.

**Counters in scope:** all three — `CounterTypeMessage`, `CounterTypeMention`, `CounterTypeReaction` — since their semantics differ (reactions already keyed off `maxOrderId`; mentions filtered by mention).

## 3. Test Level (decided)

**Hybrid.** Each scenario is a synthetic change DAG plus per-device actions. The harness builds a **real** `objecttree.ObjectTree` from the DAG and a **real** `objecttree.DiffManager` over it (the exact any-sync type `store.InitDiffManager` constructs), wired so its `onRemove` drives the **real** chat `markReadMessages`/`markReadReactions` → **real** `chatrepository` unread-count sink (reusing the existing `chatobject` test fixture's real repository/subscription/markRead, with its faked `MarkSeenHeads` replaced by the real `DiffManager`). Multiple devices are simulated by replicating `store.initDiffManagers`' per-device seenHeads-value union loop. The `sourceimpl.store`/`KeyValueService` transport-and-persistence glue is the simulated boundary (§2, §8) — it is not read-counter semantics; the semantic-bearing components (`DiffManager`, repository, chat markRead translation) are real and unmocked.

### 4.1 Scenario schema

```go
type changeKind int
const ( kindMessage changeKind = iota; kindMention; kindReaction; kindSystem )

// One change in the chat store tree. Ids are author-assigned, stable and
// content-free (the harness derives a deterministic CID-like id) so the
// hash-tiebroken sibling order is reproducible.
type scenarioChange struct {
	ID      string
	Prev    []string     // parent change ids (DAG edges); empty = root
	Author  string       // device/identity that created it
	Kind    changeKind
	ReactTo string        // for kindReaction: target message id
	Mention string        // for kindMention: mentioned identity
}

type stepKind int
const (
	stepAddChanges stepKind = iota // make changes visible to a device's local tree
	stepReadUpTo                   // device reads up to a message id (-> MarkReadMessages)
	stepMarkUnread                 // device MarkMessagesAsUnread(afterOrderId, counter)
	stepSync                       // merge seenHeads across the listed devices
	stepRestart                    // device cold-start: re-run InitDiffManager
	stepCheckpoint                 // assert
)

type step struct {
	Kind       stepKind
	Device     string
	ChangeIDs  []string            // for stepAddChanges
	UpToMsgID  string              // for stepReadUpTo
	AfterOrder string              // for stepMarkUnread
	SyncWith   []string            // for stepSync
	Counter    chatmodel.CounterType
	Expect     []checkpointExpect  // for stepCheckpoint
}

type checkpointExpect struct {
	Device      string
	Counter     chatmodel.CounterType
	WantUnread  int
	WantReadIDs []string // optional: exact read-flagged message ids
}

type scenario struct {
	Name    string
	Devices []string
	DAG     []scenarioChange
	Steps   []step      // ordered actions + checkpoints
	Intent  string      // human-authored description of the intended semantic
}
```

### 4.2 `runScenario(t, sc)` responsibilities

1. Build the real object tree from `sc.DAG` via `MockChangeCreator`/`BuildTestableTree` (one shared tree storage; each device has its own logical view but the same deterministic ids).
2. Construct a real `sourceimpl.store` over that tree + a real `chatrepository` on a temp anystore; register the three real diff managers wired to real `markReadMessages`/`markReadReactions`.
3. Model each device as an independent seenHeads value (`KeyValueService` per-device value). `stepReadUpTo` → real `MarkReadMessages`/`MarkSeenHeads` for that device's value. `stepSync` → the differ is (re)initialised seeing the **union** of the listed devices' values, exactly as `store.initDiffManagers` loops `vals`. `stepRestart` → re-run `InitDiffManager` (exercises the snapshot cache + `StoreSeenHeads`).
4. `stepCheckpoint` → read real unread counts (and optionally read-flagged ids) from the real repository for the named device/counter; record actual.
5. Compare actual to `checkpointExpect` (intended). Mismatch is recorded as a DIVERGENCE (not a hard `t.Fatal` by default — see §6), with scenario name, step index, counter, want vs got.

### 4.3 Two concrete worked scenarios (schema sanity, not placeholders)

**S-baseline-linear** — single device, linear chat.
DAG: `G(system)` ← `m1(msg,Alice)` ← `m2(msg,Bob)` ← `m3(msg,Bob)`.
Steps: Alice device adds all; checkpoint {Alice, message, unread=2 (m2,m3 — own m1 excluded)}; `stepReadUpTo m3`; checkpoint {Alice, message, unread=0, readIDs=[m1,m2,m3]}.

**S-concurrent-merge-divergence** — the key differential case.
DAG: `G` ← `m1(msg,Alice)`; `G` ← `x1(msg,Bob)` (concurrent with m1); `M(system, prev=[m1,x1])` (merge).
Steps: deviceB `stepReadUpTo x1` (seenHeads={x1}); `stepSync [A,B]`; checkpoints on both devices for `message`.
The author sets `Intent` to the **strict-DAG-ancestor** expectation (the current model's contract): reading `x1` makes read = ancestors({x1}) = {x1} only, so on device A `m1` stays unread (Alice's own `m1` is excluded from her count anyway; assert via deviceB's count where `m1` is a peer message → unread=1 for deviceB after sync, deviceA unread=0). `runScenario` records current-actual. Engine **B** keeps this MATCH (B is DAG-exact — no acceptance needed). Engine **A** (OrderId-prefix) would instead count by linear position; under A this scenario’s Intent (DAG) vs actual is the explicit owner acceptance decision and the report MUST flag it as the crux case.

## 5. Scenario Catalog (categories the dispatched agent must populate)

The catalog is generated by a dispatched agent (post-plan) as concrete `scenario` table entries, ≥1 per category, each with an explicit `Intent` and authored expected numbers:

1. Linear, single device (baseline).
2. Two devices, sequential reads, no concurrency.
3. Concurrent sends → branch, **no** merge (2 heads).
4. Concurrent sends → merge change.
5. Offline read, then sync (seenHeads union/merge).
6. Cross-device read convergence (A reads → B reflects after sync).
7. seenHead referencing a change not yet present locally (pending/notFound).
8. Read regression (`MarkMessagesAsUnread`) + re-sync.
9. Reactions counter under concurrency (own vs other; add/remove).
10. Mentions counter (mention vs non-mention messages).
11. Cold restart mid-scenario (snapshot-cache path; with and without new tail changes).
12. **DAG-ancestor vs OrderId-prefix divergence** (concurrent message sorting before/after the seen head) — explicit, the redesign’s decision case.
13. Three+ devices interleaved reads.
14. Long divergent branches then merge.
15. Own-message exclusion + author edge cases (message authored by the reading device never counts unread).

## 6. Execution & Output

- A single Go test (`TestChatReadCounterScenarios`) ranges the catalog, runs `runScenario`, and:
  - **Default mode (characterization):** records every checkpoint’s intended vs actual into `testdata/scenario_report.md` and **does not fail** on intended≠actual (those are findings, not regressions yet). It **does** `t.Fatal` on harness errors (tree build, store wiring) and on non-determinism (same scenario, different actual across two runs in-process).
  - **Lock mode (`-run … -args -lock`, opt-in):** asserts actual == previously-recorded current-actual (a true regression gate once goldens are blessed).
- The report groups scenarios by category and flags each checkpoint as `MATCH` (actual==intent) or `DIVERGENCE` (with want/got and a one-line hypothesis field for the author to fill).
- Phase deliverable: the committed report + suite, plus a short summary of the divergences that inform the redesign decision and the GO-7290 disposition.

## 7. Reuse for the Redesign

The `scenario`/`runScenario` boundary is engine-agnostic: the redesign swaps the read-counter engine behind the same `store` interface; the identical catalog runs as a differential gate. **Option B** (recommended, DAG-exact) must keep **every** scenario MATCH — any DIVERGENCE under B is a B bug, not an accepted change. **Option A** (OrderId-prefix): scenarios whose `Intent` differs from current-actual are the explicit acceptance criteria for the semantic change (with owner sign-off); the crux tripwires flipping to DIVERGENCE is the durable record of that decision. See `2026-05-16-chat-read-counter-engine-redesign-design.md`.

## 8. Risks / Notes

- The existing `chatobject` `newFixture` (`core/block/editor/chatobject/chatobject_test.go:114`) already wires a real `chatrepository`, real `storeObject` markRead, real subscription, and a real crdt anystore — but **fakes** the diff manager (its `source.EXPECT().MarkSeenHeads(...).RunAndReturn` uses a crude `msg.Id <= seen` string comparison, ~line 192). The harness extends this fixture, replacing only that fake with a **real** `objecttree.DiffManager` built from the scenario DAG (via `objecttree.NewMockChangeCreator`/`CreateRaw`/`BuildTestableTree`, the `store_apply_test.go:205` pattern). This keeps semantic code real while reusing proven wiring; constructing a fresh full `sourceimpl.store` (which needs `commonspace.Space`/`KeyValueService`) is deliberately avoided as out-of-boundary glue.
- Determinism depends on stable change ids → reproducible hash-tiebroken `Next` order → reproducible OrderId. The harness must assign ids explicitly and assert intra-run determinism (run each scenario twice, require identical actual).
- seenHeads CRDT merge is simulated as the **union of per-device values** applied via the real differ (matching `store.initDiffManagers`); it deliberately does not model KeyValueService transport/timestamp conflict resolution (out of scope, §2).
