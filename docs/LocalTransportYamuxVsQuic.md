# Local P2P transport: yamux vs QUIC — TLDR

Scope: peer-to-peer connections to **local (mDNS-discovered) peers** on a LAN or
loopback. Node connections are out of scope — QUIC is the right default there.

## Verdict

QUIC's advantages are all things a LAN and loopback do not have (loss, latency,
NAT, roaming), and its costs are worst exactly there. **TCP/yamux is the better
transport for private and loopback addresses; QUIC should stay as fallback.**

The stronger argument is not throughput — most local sync messages are small —
but **failure modes**: TCP gives refusal, reachability errors and kernel-managed
buffering for free. QUIC gives silence and a 10s timeout.

## What we actually do today

| Fact | Where |
|---|---|
| mDNS advertises **no scheme** — instance=peerId, IPs, one port, `nil` TXT | `localdiscovery.go:300` |
| Discovery rebuilds bare `ip:port` | `localdiscovery.go:341` |
| `quic://` is prefixed **unilaterally by heart**, not negotiated | `peer.go:41`, `clientserver.go:23` |
| Client listens on **UDP only** | `clientserver.go:116-132` |
| yamux `ListenAddrs` is empty → binds nothing | `config.go:632`, `yamux.go:81` |
| A TCP listen is used only to *pick a free port*, then closed | `clientserver.go:104-114,126` |
| Scheme order is **global**, not per-address | `peerservice.go:76` |
| `PreferQuic(true)` unless `PeferYamuxTransport` is set | `config.go:322` |

So local P2P is 100% QUIC/UDP today, and there is no TCP socket on that port to
connect to. "Prefer TCP on the LAN" is not a preference change — it needs a
listener first.

## Problems we have, and what each transport does about them

### 1. Hanging dials to dead peers

Peer app quits; its `ip:port` stays in the peer store. Every responsible-peers
cycle re-dials it.

- **QUIC**: any-sync opens an **unconnected** UDP socket per dial
  (`net.ListenUDP`, any-sync `quic.go:113`), so the kernel has no socket to
  attach the ICMP port-unreachable to. quic-go v0.60.0 has **zero**
  ECONNREFUSED/ICMP handling — it retransmits Initials until
  `HandshakeIdleTimeout` (10s). Capped locally by `localPeerDialTimeout` = 5s
  (`peermanager/manager.go:76`).
- **yamux**: SYN → RST → `ECONNREFUSED` in one RTT, generated by the peer's TCP
  stack. Universal, no ICMP dependency, identical on Windows.

Note quic-go's read loop *does* close a dial on any non-temporary read error
(`transport.go:544-552`) — a **connected** socket would fail fast for free.
That is the root fix, and it lives in any-sync.

### 2. Stale addresses after a network switch

Wi-Fi-era `192.168.x.y` entries are unroutable from cellular (GO-7409 field
case: all managers parked behind one dial while a healthy node connection sat
idle).

- **QUIC**: no ICMP comes back (no host to send it) → silence → full timeout.
- **yamux**: ARP failure typically surfaces `EHOSTUNREACH` well before the
  connect timeout; still not instant, but a real error rather than silence.

Neither transport fully fixes this — it is bounded by the per-dial timeout. See
GO-7410.

### 3. No refusal signal on Windows

Go's runtime disables `SIO_UDP_CONNRESET` on **every** UDP socket
(golang/go#5834), suppressing the very error a UDP-based fail-fast needs.
Re-enabling it requires a per-socket `WSAIoctl`. **TCP has no equivalent
problem.**

### 4. UDP receive-buffer drops

quic-go's well-known warning: the kernel UDP receive buffer defaults to ~200 KB
on Linux; when it fills, the kernel silently drops packets. TCP buffering is
kernel-managed and self-tuning.

### 5. Loopback efficiency

| | value |
|---|---|
| `lo0` MTU (macOS) | 16384 |
| loopback MTU (Linux) | 65536 |
| quic-go datagram cap | **1452** (`internal/protocol/protocol.go:114`) |
| quic-go initial packet size | 1280 (ours: 1200, `config.go` `GetQuic`) |

Path MTU discovery cannot exceed 1452. For the same payload over loopback QUIC
sends ~**11× more datagrams than TCP on macOS, ~45× on Linux**, each a syscall
with userspace crypto and ACK bookkeeping — and **GSO is Linux-only in
quic-go**, so macOS/Windows/iOS/Android cannot amortize it.

Third-party numbers, encrypted-vs-encrypted (the right baseline, since we run
noise over yamux): raw TCP 708 Mbps, TLS 1.3/TCP 466 Mbps, off-the-shelf QUIC
**196 Mbps (42%)**; recovered to 464 Mbps only via delayed ACKs + GSO +
1460-byte packets. See Fastly, "measuring QUIC vs TCP computational efficiency".

### 6. Latent: TCP port picked, UDP port bound

`prepareListener` picks a free **TCP** port, closes it, then binds **UDP** on
that number. A free TCP port does not imply a free UDP port. If UDP N is taken,
`ListenAddrs` errors, `startServer` fails, and `Run` logs at Info and returns
nil — the app silently comes up with **no local P2P server at all**.

## What QUIC would buy on a LAN (and why it does not)

| Feature | Why it does not apply locally |
|---|---|
| 0-RTT / faster handshake | saves ~1 RTT; LAN RTT <1ms, loopback ~0 |
| Connection migration | if you roam off the LAN the peer is gone; mDNS re-discovers |
| No head-of-line blocking | only pays off under loss; LAN ≈ 0, loopback = 0 |
| NAT traversal / hole punching | mDNS peers are directly addressable |
| Survives TCP-blocking middleboxes | not a LAN concern |

Zero-loss is the decisive one: with no loss there is no congestion to recover
from, so QUIC's per-stream flow control is pure added overhead.

QUIC stays justified for **node** connections, where mobile Wi-Fi↔cellular
roaming makes connection migration real.

## Status

**Done — GO-7421** (`c396cb040`, branch `go-7421-udp-probe-local-peers`):
pre-dial UDP liveness probe (`net/udpprobe`). Connected UDP socket + one
throwaway datagram; ECONNREFUSED/WSAECONNRESET ⇒ provably dead ⇒ skip the dial.
Asymmetric by construction — Dead only on proof, Inconclusive on any doubt, so
it can only skip dials that were guaranteed to fail. Scoped to
loopback/RFC1918/link-local. Also picks an existing live connection before
probing or dialing.

**Not done — yamux on the LAN.** Would subsume GO-7421's main win (a real dial
replaces the heuristic: no TOCTOU, no inconclusive bucket, no Windows
`WSAIoctl`). Blockers:

1. Bind a yamux listener on the same port number (`GetYamux().ListenAddrs` is
   empty today). The existing picker already proved TCP N free at startup.
2. **Per-address scheme ordering** — `preferredSchemes()` is one global order.
   Emitting both `yamux://` and `quic://` per local address is heart-side and
   easy, but the global flag still decides which is tried first (currently
   QUIC — i.e. backwards for this purpose). Needs a small any-sync change to
   `Dial`.
3. Version skew is self-healing *if* ordered right: new client dials yamux, old
   peer has no TCP listener, instant RST, `dialScheme` falls through to QUIC.
4. Risks to weigh: second listener on mobile, possible fresh firewall prompt for
   TCP on Windows/macOS. iOS Local Network permission is not a blocker —
   `selfconnect.go`'s existing restriction probe is already TCP.

## Caveat

The performance figures above are third-party plus two locally verified
constants (`lo0` MTU, quic-go's 1452 cap). **Our stack has not been measured.**
A yamux-vs-quic benchmark over loopback with a realistic sync payload would
settle it before committing to the listener change.
